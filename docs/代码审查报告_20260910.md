## 2. 逻辑与正确性（5.0 / 10）

### 2.1 做得对的部分（先说好话，因为这部分确实好）

1. **契约兼容性设计**：`RlState` 保留 `LEGACY_STATE_DIM=16` / `OLD_STATE_DIM_18=18` 并允许按前缀截断喂给旧模型（`RlBrain:147-155`、`:435-442`），`RlModel.load` 对大端布局逐字段对齐 Python 导出（`train_ppo.py:421-422`）；`RlActionSlot` 把"动作槽"与"技能身份"解耦，`slot_stable` 让同一槽位跨时间指向同一技能——这些是踩过坑之后才会有的设计。
2. **半写文件的防御**：`RlDataRecorder.flushToDisk` 先写完整缓冲再关闭；Python 侧 `read_exact + EOFError`（`train_ppo.py:55-60`）在五个脚本中一致地把截断文件判为损坏而非读出垃圾——这是对的。
3. **硬约束兜底**：`RlBrain:181-215` 的"倒地强制翻滚 / 无目标不空挥 / 近战武器不回退远程"三道硬约束写在模型输出之后、执行之前，是典型的"AI 不能违反的物理规则"，方向正确。
4. **事故驱动的修复痕迹**：`ItemCombat` 中"V54 追加（12:28 crash 实证）"的 `instanceof BlockItem` 保护（`:216-218, 272-274, 320-322`）确实堵住了 `ClassCastException` 崩服路径。

### 2.3 并发安全

- **结论：RL 决策链本身是"主线程独占"，但项目存在一个真实的跨线程写入点（AutoTicker）**——并发风险不是"已经出错"，而是"结构上没有被约束"。
- **RL 决策链**：状态在服务器主线程上读写（`RlBrain.tick` 来自 `MaidTick`；`ItemCombat.throwPearlAt` 经 `server.getServer().execute()` 回到主线程；`RlCommand` 在主线程执行）→ 当前无竞态。
- **跨线程写入点（P1）**：`AutoTicker` 的 `eftlm-auto-ticker` 守护线程上执行了 `server.getTickCount()`、`server.tickTimes` 数组的 `clone()+sort`（与服务端线程写入并发）、**经反射改写 `MinecraftServer.nextTickTime`/`lastTime`**、修改全局倍率（`TickAccelerator.setMultiplier`）。正确做法是把状态写入经 `server.execute(...)` 投递回服务端线程，仅在"服务器已完全卡死"时保留反射作为最后手段并显式注释这是唯一例外。详见 9.4-①。
- **静态可变全局状态遍地**（且全是非线程安全 `HashMap`）：`RlBrain` 7 个 Map、`TargetTracker.PER_MAID`、`CombatLibrary.STATES/HIT_EXP`、`RlDataRecorder` 4 个 Map、`RlTrace.BUFFERS/PENDING_EXEC`、`ItemCombat.STATES`、`SpatialMap.HAZARDS`、`EfnSkillCatalog.SKILL_COOLDOWNS`、`ReactiveLayer.STATES`。目前靠"只在主线程访问"维持，但**没有任何注释、断言或封装表达这个约束**。
- **锁定策略自相矛盾**：`CombatLibrary.reset()` 加 `synchronized`，而 `recordHit/canReach/shouldMaskSlot` 不加；`RlBrain.reloadModel()` 加 `synchronized`，而 `model` 字段的读取不加；`RlConfig.ensureLoaded()` 用双重检查锁 + `volatile`（✅ 正确），但其余 `public static` 字段被命令处理器直接改写。说明作者对"哪些状态需要保护"没有统一结论。
- 结论：**当前无活跃竞态**，但并发正确性完全依赖纪律而非结构（无 `@MainThread` 注解、无主线程断言、无状态归属文档），在有 8 倍加速与看门狗自救的复杂时序下，这是下一次事故的温床。

## 3. 架构与设计（6.0 / 10）

### 3.1 资产：分层与扩展点

```
感知(每tick)  TargetTracker / ProjectilePerception / SpatialMap
   ↓
反应层(每tick, 规则, 可抢占)   ReactiveLayer —— 起身防御 / 前摇规避 / 弹道拦截, 抢占后 6t 不输出 RL
   ↓
战术层(5tick, RL)  RlBrain(32维→MLP→64动作) + 掩码(无效槽/命中经验/连段后摇)
   ↓
战略层(40tick, 规则)  StrategicLayer —— 霸体切近战 / 放风筝切远程 / 低华丽度换武器 / 方块武器
   ↓
执行层  事件总线 RlActEvent → RlActionRegistry(执行器注册表) → Generic/Efn/Defense 执行器
   ↓  CommitmentCatalog 门控(前摇/判定/后摇/可打断)
反馈   RlExecResultEvent → s[16]/s[17] + 奖励回填；RlDataRecorder 轨迹 v2 → train/ → 热重载
```

**三个真正的设计优点**：
1. `RlActionExecutor` 接口 + `RlActionRegistry.register`（`:49-61`）：新增战斗状态机只需实现 3 个方法即可进入动作空间，且**模型输出维度不变**（`TOTAL_ACTIONS` 恒定）——这是把"动作空间演进"与"模型契约"解耦的正确做法。
2. 反应层"抢占式防守 + busy 窗口"（`ReactiveLayer:44-47, 146-150`）：把"生存底线"从 RL 手里拿走，避免模型在受控窗口里输出无意义动作，同时用 `s[17]` 让模型学会"什么时候出招不会被打断"——规则与学习的职责切得干净。
3. 规则层不污染轨迹（README 与 `CombatLibrary` 类注释反复强调；`RlBrain:233-235` 的 arena 过滤）——这是很多 RL 项目栽跟头的地方。

### 4.3 权限校验

- `/rl`（`RlCommand:29-59`）与 `/arena`（`AutoArena:224-244`）**均要求权限等级 2** ✅，且命令不含文件路径/任意值写入（`/rl tickrate` 有 `floatArg(0.1,10)` 范围约束，`/rl autotick max|min` 有 `floatArg` 约束 ✅）。
- 唯一的"权限放大"点是**配置文件即代码执行面**：`rl.properties`/`arena.properties`/`course.json` 位于可写目录，`course.json` 的 `suggested_entities` 直接决定刷什么实体（`loadCourse:337-351`），含黑名单过滤 ✅；`model_file` 支持绝对路径 → 模型文件即"可加载的任意路径二进制"，配合 C-9 的分配无上限，构成"本地文件→OOM"路径（需要本地写权限，风险等级低）。
- 反射面：`AutoTicker` 用反射 `setAccessible` 改写 `MinecraftServer` 私有字段；`EfnSkillCatalog`/`CommitmentCatalog` 反射/强转第三方动画对象。这些都是**对已安装模组的信任假设**，没有被外部输入驱动，可接受；但 `NullEntityMixin` 等对第三方类的注入需保持 `@Pseudo`+`required:false`（现状正确，见分册）。

### 4.4 世界写入与侧信道

- `ItemCombat`：临时方块 3 tick 后强删（P0-5）、垫高柱用 `teleportTo` 直接把女仆抬升（`placePillar:453-455`，绕过碰撞与可站立性检查）、放水灭火（水体可能流动扩散后残留）——**竞技场内可接受（虚空平台），生产环境需开关隔离**。
- `AutoArena`：**服务端启动即无条件 `discard()` 出生点 1024×128×1024 内的全部女仆与非女仆 Mob（P0-7）**，无归属判定、无开关、无二次确认——对训练专用服是"清理残留"，对普通存档是**不可恢复的丢档**；同时强制加载 289 个区块（`setChunkForced(true)`，无对应 `unforce`），该状态会写进存档并持续生效。**这是本报告认为最需要先处理的一类"发布即破坏"行为。**

### 5.4 算法复杂度

- **无明显 O(n²) 热点**；`recordHit`/`canReach` 的桶查找是 O(72) 线性扫描（可换 HashSet 键，收益微小）；`selectPriorityTarget` 内层重复计算 `best.threatScore * confidence`（`TargetTracker:156-157`，可读性差但 O(n)）。
- `train/collect_data` 对每条轨迹做 `np.bincount(a)`（`train_ppo.py:131`）→ 若动作含负值直接 `ValueError` 崩（契约校验缺失，见 4.3/分册）。

### 5.5 稳定性放大项（性能问题如何变成"停机"）

本项目把"性能"与"稳定性"耦合成了一条链：`tick 95%ile` → AutoTicker 升降档 → 虚拟时钟 → tick 节流等待。链条上有一处**自反风险**：降档会不连续地压缩虚拟时间轴，而 `nextTickTime` 携带旧倍率下的数值，可能让 tick 循环进入长等待/停滞；项目已有"15 秒后反射时钟复位"与 guardian 重启作为兜底（README 自述事故链），但那意味着**保护动作本身可能触发它要防的停滞**，且兜底依赖反射改写私有字段。详见 9.4-②；建议把"改倍率"与"重置 `nextTickTime`"合成同一个原子操作，使降档天然安全。

## 9. 逐子系统审查结论

**关键结论补充**：
- `CommitmentCatalog`（167 行）是本次架构重写中最有价值的落地件：把"前摇/判定/后摇/可打断"从运行时动画对象读出来统一门控，且失败时保守默认（`0.3s/0.3s/0.5s/不可打断`）。它的不足是**只用于"拒绝"，没有用于"排队"**（报告 3.6 承诺的 `reserveAnimation` 意图队列未实现），因此"不可打断帧里想接的动作"只能靠 5 tick 后重新决策，模型学到的是"等"，而不是"承诺后接续"。

**关键发现**：
- **EF-1 [P1][正确性/数据质量][`EfnSkillCatalog.java:291-302`、`CommitmentCatalog.java:75-77`、`SkillSpec.id()`]** **技能 `id` 在目录内不唯一，却被同时用作"技能冷却键"与"承诺帧缓存键"**。审查者已独立复核：`hf_blade` 内 `slash_lr_down`/`slash_lr_up`/`slash_left`/`slash_mid`… 各出现 **2 次**（diagonal 与 horizontal 是不同动画），`hf_murasama` 有 **14 个**重复 id，`sekiro` 有 **8 个**。后果有三：① 两个不同动画共享一个冷却槽（一个放完另一个也被冷却）；② `CommitmentCatalog` 把 A 动画的前摇/判定/后摇返回给 B 动画（掩码与门控用错帧数据）；③ **轨迹的动作标签 `slot.label()` 就是 `spec.id()`**，于是训练数据里两个不同动作带同一个标签，`train_ppo.collect_data` 的"标签→槽位"重映射会把它们映射到同一槽位——**这是训练数据层面的语义污染**，而不只是显示问题。修法：以 `animKey`（唯一）作为冷却/缓存键，或把 `id` 规范为 `武器目录:技能名`（并对目录加载做唯一性校验，重复即 ERROR 并保留先出现者）。
- **EF-2 [P2][正确性][`EfnSkillCatalog.java:291-302` + `RlMemoryCleanup.java:30-33`]** 技能冷却以 `maid.tickCount` 为时钟，而 `tickCount` **不写入 NBT**（实体重载后归零），清理又只覆盖 `KILLED`/`DISCARDED`——**区块卸载重载**（`RemovalReason.UNLOADED_TO_CHUNK`）不会清理冷却表：`last` 仍是旧的大数值而 `tickCount` 归零 → `last + cooldown > tick` 恒成立 → **该技能被"锁死"数万 tick**。修法：冷却改为记录"墙上时间/游戏总刻（`level.getGameTime()`）"或在实体重载时重置该女仆的冷却表。
- **EF-3 [P2][正确性][`EfnSkillCatalog.java:124-146`]** 空文件/截断的 `skills.json` 会让 Gson 返回 `null` root → `parse` 返回三个空 Map → 日志只有一行 `0 weapons`，且该空目录被 `INSTANCE` **永久缓存**（不会自动重试）→ 全部武器技能静默失效。修法：`root == null` 时明确 ERROR（含文件路径与大小）并拒绝替换旧目录。
- **EF-4 [P2][正确性][`EfnAnim.java:17-49`]** 动画 accessor 缓存**无失效机制**，而 `AnimationManager` 是资源重载监听器：资源重载后缓存里可能是失效 accessor（代码自己在 `dump()` 里用 `isPresent()` 判可用，说明作者知道这个风险）。
- **EF-5 [P2][死代码][`EfnCompat.java:9-24, 85-117`]** **16 个本地武器类中有 10 个从未被实例化**（`Yamato`/`HfBlade`/`Murasama`/`BroadBlade`/`Pioneer`/`Kusabimaru`/`Aetherialdusk`/`Beastclaw`/`Bloodlust`/`Ruinsgreatsword` 只被 import，注册时改用了 EFTLM 自带的同类），10 条 import 亦未使用——这 10 个文件（约 300 行）连同注释里的"技能表 §x"一起构成**会误导维护者的僵尸代码**（改它们不会产生任何效果）。
- **EF-6 [P2][配置双源风险][`EfnSkillCatalog.java:124-140`]** 技能目录**优先读 `config/eftlm_stylish/skills.json`，存在时完全遮蔽 jar 内默认版本**。模组升级后若 config 目录残留旧文件，会静默使用旧技能表，且没有版本号/哈希比对或告警。建议：两个来源都解析，日志输出 `version` 与条目差异。
- **EF-7 [P3][错误信息误导][`EfnSkillCatalog.java:126-139`]** `getResourceAsStream(DEFAULT_RESOURCE)` 返回 null 时构造 `InputStreamReader(null, …)` 抛 NPE，被 `catch (Exception)` 记录为"failed to load skills.json"——真正原因是"jar 内资源缺失"。
- **EF-8 [P3][封装泄漏][`EfnSkillCatalog.java:245-270`]** `skillsFor`/`skillsOf` 直接返回目录内部 `List<SkillSpec>`（未做不可变包装），调用方一旦 `sort`/`clear` 就会污染全局目录。
- **EF-9 [P3][语义混淆][`DefenseSkillExecutor.java:36-45`]** `dodge_step`/`blade_clash` 是防守**动作**，却用 `SkillSpec(animKey="ef_tlm:dodge_step")` 挂进"技能"通道，导致 `CombatLibrary.shouldMaskSlot` 解析一个并不存在于动画注册表的 `ResourceLocation`（当前"永不掩码"，无害但混乱）。建议 `SkillSpec` 增加 `kind` 字段区分 ANIMATION/DEFENSE_ACTION。
- **EF-10 [P2][可扩展性][`compat/efn/weapons/*`、`compat/wom/*`]** 36 个武器适配类共约 1200 行几乎全是"行为表 series 声明"的样板，且与 `skills.json` 构成**双数据源**（例：`BroadBlade.java:28-37` 登记 9 个普攻，而 `skills.json` 的 broadblade 只有 6 条）。建议数据驱动（JSON + `/efskills reload`），把"加武器"从"改 Java + 重新编译 + 重新部署"降为"改 JSON + 热重载"。
- **正面**：`EfnSkillCommand`（`/efskills dump|reload|stats`，权限 2）把"技能目录侦察—重载—统计"做成了运维闭环；并行深审另外实证了两件"没问题"的事——16 个武器类共 116 处 `EfnAnim.byKey(...)` 的动画键**全部命中** EFN 3.4.0 / Enhance 包内的 526 个动画 JSON，`EfnCompat` 注册的 33 个物品名**全部存在**于 `EFNItem` 常量池——说明"字符串键 + 运行时校验"的兼容策略在真实产物上是站得住的。

### 9.4 工具与 Mixin（`util/AutoTicker`、`util/TickAccelerator`、`util/AnimKit`、`mixin/*`）

| 子维度 | 分 | 依据 |
|---|---|---|
| 正确性 | 4.5 | 时钟虚拟化方案本身正确（以 `Util.getMillis()` 为同源基准，倍率 1.0 时严格恒等——这是踩过"epoch 大数 vs 小数"坑之后的正确解）；但**看门狗阈值单位混淆**（下②，代码可验证）、**反射字段扫描脆弱**（下④）、**采样失败被当作"健康/空闲"**（下⑤）、**倍率变更重标定时间轴**（下③）——四条都指向"保护机制本身可能误动作或静默失效" |
| 架构 | 5.5 | 决策（AutoTicker）与执行（TickAccelerator）分离正确；`AutoTicker` 单类混装采样、决策、反射复位、文件写入、线程转储 5 种职责 |

**本子系统的独立发现**（①③⑦⑧ 为审查者本人精读确认；②④⑤⑥ 由并行深审给出，其中 ② 已由审查者按代码算术复核）：

1. **[P1][并发][`AutoTicker.java:174-270, 293-327`]** 自动调度器跑在独立线程 `eftlm-auto-ticker`（`SCHEDULER.scheduleAtFixedRate`），却在该线程上：`server.getTickCount()`、`times.clone()` 排序（与服务端线程写 `tickTimes` 并发）、**经反射写 `MinecraftServer.nextTickTime`/`lastTime`**、改全局倍率。这与项目"一切在主线程"的隐含假设冲突：正确做法是经 `server.execute(...)` 把状态写入投递回服务端线程（反射复位只在"服务器已完全卡死"时作为最后手段，并显式注释这是唯一例外）。
2. **[P1][正确性/单位][`AutoTicker.java:212-240` + `RlConfig.java:163`]** 看门狗判断式是 `streak * intervalSec >= watchdogStallTicks/2`（`streak` 的单位是"采样周期数"），阈值语义是**秒**——两者只在 `intervalSec=5` 时大致等价。而 `RlConfig` 允许 `auto_tickrate_interval` 到 **120 秒**：此时**只要两次采样之间少 1 个 tick（`streak=1`）**，`1×120 ≥ 15` 立即触发时钟复位、`≥30` 立即写 `watchdog_alarm.txt` → 外部 guardian 误判并重启服务器。修法：看门狗改用**真实墙上时间的停滞时长**（`now - lastTickAdvanceWall`），与 `intervalSec` 解耦。
3. **[P1][正确性][`TickAccelerator.java:66-68` + `AutoTicker.java:252-265`]** `virtualNow()` 是 `Util.getMillis() × multiplier` 的**不连续函数**：降档瞬间虚拟时间轴被整体压缩，而 `nextTickTime` 仍带着旧倍率下的数值 → 等待条件可能长期成立。项目自己的事故报告（README "加速死锁根因与修复"）已经证明这类停滞在本环境会"双双冻结、降档无效"，最终靠**15 秒后反射把 `nextTickTime` 置 0** 自愈。也就是说：**"降档"这一保护动作本身就在制造它要防的那种停滞**，而 guardian 的应急逻辑（`TPS<15 → RCON /rl tickrate 1.0`）恰好是同一路径。建议：倍率变更与时钟复位合成**同一个原子操作**（改倍率时同步 `nextTickTime = virtualNow + 50`）。
4. **[P1][健壮性][`AutoTicker.java:302-322`]** `resetTickClock` 用"遍历 `MinecraftServer` 全部声明字段 + 按名字匹配，且**不 `break`、不看类型**"的方式定位 `nextTickTime`/`lastTime`，别名表里混入混淆名 `ai`/`ah`；只要映射环境变化或存在同名无关字段，就可能写到错误字段；且 `f726` 未找到时仍 `return true`（返回"部分成功"却对外表现为复位成功）。建议：加 `break` + `f.getType()==long.class` 校验 + 日志区分"完全成功/部分成功/失败"，并把字段句柄缓存一次（避免每次全字段扫描）。
5. **[P1][可观测性][`AutoTicker.java:329-358, 243-250`]** `readTick95Ms()` 失败返回 `-1`、`readSystemCpu()` 失败返回 `0.0`（=空闲）：CPU 采样一旦失效，`cpuIdle` 恒真，在 `tick95` 仍可用且健康、TPS 达成时会**持续升档**而不受 CPU 负载约束。失败应视为"未知→保守降档/冻结"，并在 `/rl autotick status` 中显式显示"采样不可用"。
6. **[P1][可观测性][`eftlm_stylish.mixins.json:2` + `EftlmMixinConnector`]** 四个 mixin 全部 `@Pseudo`/`targets` 字符串，配置 `required:false`，经 `IMixinConnector` 提前注册，并实证 `build/libs` 内 `refmap` 为空（`{"mappings":{}}`，因全部 `remap=false`）——**没有任何启动期断言能证明"加速/呼吸修复/第三方补丁真的生效了"**，而 `defaultRequire=1` 只保证"注入点找不到会报错"，不保证"注册通道本身没走丢"（V-3 的双份 `mixins.json` 正是这条风险的现实载体）。建议：`ServerStartedEvent` 中做启动自检（`TickAccelerator.active()` 且倍率 1.0 时 `virtualNow()==Util.getMillis()`；非 1.0 时日志打印实际倍率与实测 TPS），失败则 ERROR 告警。

8. **[P1][时钟同源][`TickrateMixin.java:54-86`]** 该 mixin 只虚拟化 `runServer`(`m_130011_`) 的 `ordinal=0/2` 与 `prepareLevels`(`m_129940_`) 的调用点，**刻意保留 `ordinal=1`（"Can't keep up" 落后检测）为真实时钟**（注释理由：避免误触发追赶修正）。并行深审以 `MinecraftServer` 字节码给出偏移实证：`m_130011_` 的 3 处 `Util.m_137550_()` 分别为 ① `lastTime` 初始化、② 落后检测（`-lastTime > 2000ms`）、③ `Math.max(getMillis()+50, lastTime)` 写 `nextTickTime`——**保留 ② 为真实时钟、而 ① ③ 被虚拟化，等于让"真实 vs 虚拟"在同一个表达式链上相遇**，倍率 >1 时可能周期性误报 "Can't keep up" 并触发追赶修正（倍率 <1 时该修正还会在数学上"补掉"减速效果）。同时 `m_129940_` 内实测有 **4 处** `Util.getMillis()`（注释声称只有 1 处），全部被虚拟化 → 启动期 chunk 加载的 `+10ms` 轮询节奏在 8× 下被压缩 8 倍，重负载时可能影响世界加载。
   **建议**：用 `@ModifyArg`/`@ModifyExpressionValue` 精确改写"写 `nextTickTime` 的那一次求值"，或把落后检测一并纳入虚拟时钟域以保证同源；`prepareLevels` 的注入点单独处理（仅在服务器已启动完成后缩放）；并把字节码偏移实证写进注释与验收用例（8× 档位下 grep 日志确认无 "Can't keep up"）。

**关键发现**：
- **AR-1 [P2][热路径]** `AutoArena.onServerTick:554-595` 每 20 tick 做两轮"每种标靶类型 × 全图 `getEntities`"遍历（第一轮仅当 `maid.getTarget()==null`，**第二轮对 Boss 强制仇恨是无条件执行**），每轮都 `ResourceLocation.parse(id)` 且未缓存 `EntityType`；`pullStrayTargets:996-1001`、`countAliveTargets:1030-1035`、`maintainCage`、`findNearestTarget` 各自再来一轮。**这是本项目最大的一处"全表扫描集群"**（≈15 次/秒），改法：`entityIds` 预解析缓存 + 复用 `TargetTracker` 已维护的目标列表 + 合并遍历 + AABB 约束。
- **AR-2 [P1][正确性/输入校验][`AutoArena.java:383-402`]** `findNearestTarget` 对配置/课程下发的实体 id 直接 `ResourceLocation.parse(id)`（非法字符抛 `ResourceLocationException`，已由并行深审 javap 实证 parse 会强校验）并 `(LivingEntity) e` 强转（非生物实体抛 CCE）。该方法被 `AutoSkill:129`（每 tick）与 `StylishConditions:120` 调用 → **异常直接进入行为表/决策热路径**。修法：`ResourceLocation.tryParse` + 注册表 `EntityType` 的 `baseClass` 白名单 + `instanceof LivingEntity`。
- **AR-3 [P1][评估有效性]** `/arena stats` 的胜利指标口径不可靠：`win_rate = kills/(kills+deaths)`，其中 `statsKills++` 只要击杀者是**任意女仆**（含影子女仆、自适应对手女仆，`:261-263, :274-276`），而 `statsDeaths` **只统计"绀珠之药耐久下降"这一条路径**（`:603-616`），且并行深审进一步指出 `lastElixirDur` 会被自适应对手的重生逻辑（`:958-960`）重置 → 对手每 200 tick 重生一次就凭空多记一次"死亡+复活"。**结论：训练决策所依赖的"胜率"系统性虚高**。建议：统计按 UUID/角色分桶，死亡以 `LivingDeathEvent` 为准，指标按课程轮次给窗口值。
- **AR-4 [P1][跨世界状态][`AutoArena.java:126-151, 418-465`]** 全部竞技场静态状态（`cageGrowthTick`/`arenaMaidId`/`shadowMaidId`/`adaptiveMaidId`/`spawnNow`/统计计数/`lastElixirDur` + `AutoSkill.testCursor` 等）**在 `onServerStarted` 中没有一处重置、也没有 `ServerStoppingEvent` 钩子**：`cageGrowthTick` 保留上一世界的值而新世界的 `tick` 从 0 开始 → 差值恒负 → 斗兽场在该世界**永不扩圈**（最长 `cageGrowthTick/20` 秒静默失效）。集成服/单机反复进出世界即可复现。
- **AR-5 [P2][内存泄漏]** `STRAY_TICKS`（`:986`）以标靶 UUID 为键，只在"标靶回到 8 格内"时 `remove`（`:1018`）；若标靶**在游离状态被击杀/移除**（正是放风筝场景），条目永久驻留——每个标靶 UUID 一生只出现一次，等于与训练时长成正比的缓慢泄漏。
- **AR-6 [P2][配置语义漂移][`AutoArena.java:534, 687`]** 20 tick 闸门与 `tick % interval == 0` 叠加 → 实际补刷间隔是 `lcm(20, interval)`（`interval=250` → 500 tick，`130` → 260 tick），配置项语义与注释（"下个 tick 补标靶"实际最多晚 20 tick）都不成立。
- **AR-7 [P2][可维护性/事实错误][`StylishCombatSkill.java:494-497` vs `AutoArena:405-416`]** 存在**两套语义相反的"是否竞技场标靶"判定**：`StylishCombatSkill` 硬编码 `id.startsWith("annoyingvillagers:")`，而 `AutoArena.isArenaTargetEntity` 按 `entityIds` 匹配（`TargetTracker:256` 在用）。课程把标靶换成原版生物后，两处结论相反 → 攻击/锁定判定与追踪层不一致。
- **AR-8 [P2][性能/存档副作用][`AutoArena.java:453-459`]** 289 个区块 `setChunkForced(true)` 全仓唯一且**没有对应的 unforce**：强制加载状态写入存档 `ForcedChunksSavedData`，即使之后 `enabled=false` 也继续生效（永久改变存档行为）；`buildPlatform/growPlatform` 的逐格写方块（默认 441 次 `setBlockAndUpdate` + 10125 次 `getBlockState` 清墙；flat 模式 9409 次 `UPDATE_ALL`）全部在 `ServerStartedEvent` 的服务端线程上同步执行。
- **AR-9 [P2][方法论]** 影子评估宣称是"双女仆 A/B 对比"，但主/影子/对手**共享同一批全局状态**：`CombatLibrary.HIT_EXP`（命中经验桶，跨女仆全局累积）、`SpatialMap.HAZARDS`（全局危险区），以及同一竞技场里的目标竞争。因此 A/B 差异里混入了"共享经验导致的同质化"与"目标竞争干扰"，**不能直接当作模型优劣的证据**。建议按女仆/评估轮次隔离命名空间。
- **AR-10 [P2][策略层]** `StrategicLayer`（40 tick 规则层）会**绕过 RL 直接改变物理状态**（霸体切近战/放风筝切远程/低华丽度换武器），但 32 维状态里没有"本 tick 战略层是否插手"的标志位，模型无法区分"我自己换的武器"与"战略层替我换的"——这也是"规则层不进训练数据"这一原则的漏洞：动作没进轨迹，但状态被它改变了。
- **AR-11 [P2][奖励分散]** 奖励常量分布在 `RlBrain`（熵/衰减/防守/距离/熔断）与 `StylishCombatSkill`（命中 `+30/+10/+2`、突进 `+50`、击杀 `+100`、切换连携 `+15`、被击倒/受击 `-30`）两处，**没有单一奖励表**，无法在不改代码的情况下做奖励消融实验。
