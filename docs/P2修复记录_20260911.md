## 0. 本轮最重要的发现：一个"看起来生效、其实从未生效"的门禁（已修）

P1 阶段我给部署门禁加了「语义纪元变更 → 重建 acc 基线」分支（`iterate.py:537-544`），
并在 `train_ppo.py` 里定义了 `SEMANTICS_EPOCH = 2`，昨天还按它向用户汇报"新纪元基线不会误杀"。
**实际上这个分支永远不可能触发**：

- `train_ppo.py:429-430` 把 `semantics_epoch` 放进 `metrics`，
- 紧接着 `:439`（`if eval_data is not None:` 分支内）执行 `metrics = {"acc": …, "nll": …}`
  —— **重新绑定**，把 `semantics_epoch` / `critic_restored` 覆盖掉；而 `main()` 永远传 `eval_data`；
- `:650-653` 真正落盘的 JSON 里也只写 5 个键，**没有** `semantics_epoch`。

于是 `new.get("semantics_epoch")` 恒为 `None` → 门禁退化成"拿旧 acc 基线比较"。
**今晚 19:03 那轮就会被误杀**：它吃的是"强制等待步已排除"的新语义数据，eval_acc 预期
~0.70，而旧基线是 0.878 → `0.70 < 0.878 - 0.02` → REJECT。

修复（`train_ppo.py`）：

1. `:439` 改为 `metrics.update({...})`（合并而非覆盖）；
2. 落盘 JSON 增写 `semantics_epoch` / `critic_restored` / `traj_version` / `state_dim` / `num_actions`；
3. 给 `selftest_contract.py` 增加第 [4] 节，把这类"键从未落盘"的事故固化成断言
   （用 `ast` 解析 `train_ppo.py` 里真正被 `json.dump` 的那份字典，并核对 `iterate.py` 确实读这个键）。

**为什么值得单列**：这不是"少写一个字段"，而是"门禁静默失效 + 汇报与事实不符"。
静态可查的契约断言（第 [4] 节共 9 条）现在是每轮训练前的预检项（`iterate.py:356-360` 已接线）。

## 1. P2-6 全局共享状态命名空间隔离（AR-9，已改完，待部署）

审查报告 AR-9：影子评估宣称"双女仆 A/B 对比"，但主/影子/对手共享全局状态，
差异里混入"共享经验导致的同质化"，**不能作为模型优劣证据**。本轮修掉两处 + 一处归因错误。

### 1.1 `CombatLibrary.HIT_EXP`：全局命中经验 → 按女仆隔离

- 原状：`private static final Map<ResourceLocation, List<HitBin>> HIT_EXP`（`CombatLibrary.java:71`），
  键只有动画注册名，进程内**所有**女仆共享；而它直接驱动 `shouldMaskSlot`（动作掩码，每个决策都调）
  与 `expScore`（规则调度排序）→ 一个女仆打出的经验会静默改写另一个女仆的**动作空间**。
- 另有两个存量缺陷：`reset()` 无任何调用者（唯一的全局清理钩子不可达）；
  `forget(UUID)` 只清 `STATES` 不清 `HIT_EXP`（**命中桶永久驻留**）。
- 现状：`Map<UUID, Map<ResourceLocation, List<HitBin>>>`，按女仆 UUID 分表；
  新增配置 `hit_exp_scope`（`maid`=默认隔离 / `global`=旧行为，便于对照组与复现旧实验）；
  `forget(UUID)` 同表清理（已由 `RlBrain.forgetMaid:547` 接线）；
  `status()` 改为跨表汇总并显示 `scopes=`。
- 桶数天然有界：距离档 `0..MAX_DIST_BIN` × 8 扇区，**不存在无界增长**（原报告的"泄漏"指分表前的驻留）。

### 1.2 `SpatialMap.HAZARDS`：顺带修掉一个真时钟混用 bug

- 原状：`List<Hazard>` 只有 `{pos, radius, until}`，**无归属、无维度**；
  `until` 用**登记方**女仆的 `maid.tickCount` 盖章，查询/清理用**调用方**女仆的 `tickCount` 比较。
  不同女仆 `tickCount` 起点不同（实体重载归零）→ "谁先 tick 谁说了算"：
  条目可能瞬间过期（无害）或**长期滞留**（把安全格判成危险区 → 闪避方向选反）。
- 现状：`Hazard{owner, dim, pos, radius, until}`；时钟统一为**维度游戏刻** `level.getGameTime()`；
  查询按 `owner + dim` 过滤；`registerHazard(maid, pos, radius, durationTicks)` 传**时长**而非绝对刻
  （调用方不再各自算时钟）；查询路径顺手清理过期项（不再依赖"某个女仆恰好调用 prune"）；
  加 512 条上限兜底。4 个调用点全部更新（`ItemCombat` 的 3 处登记 + 1 处 prune）。

### 1.3 `RlBrain.FORCED_WAIT`：归因错误（P1 自己引入的观测项）

P1 加的强制等待计数器是**单个全局 `AtomicLong`**，而心跳在 `tickCount % 100 == 0` 时
`getAndSet(0)` —— 任何女仆跨过该边界就把**所有人**的增量一起领走，
于是 `forced_wait_skipped=` 被错误归因到"恰好打印的那个女仆"。现改为按女仆计数（`forgetMaid` 同清）。

## 2. P2-4 契约版本化（Python 侧已完成；Java 侧天然容忍尾部扩展）

盘点结论（两个只读子代理给出的精确坐标）决定了实现方向：

- 模型文件：Java `RlModel.load` 的尺寸校验是**一边倒**的（只拒 `actual < expected`），
  所以**追加**尾部字段对旧 JVM 安全；而**前置**字段会被读成 `numLayers` 并静默错位（危险）。
  Python `load_model_bin` 原本**零校验**。
- 轨迹文件：读取端读完已知字段即停、从不读到 EOF → 尾部字段被忽略；但
  `traj_io.load` 把**任何**未知首整数当 v1（`n = first; version = 1`），
  于是将来写出的 v4 头会被解析成 v1 垃圾，**并且**因 `version < CURRENT_VERSION` 被错误地做一次奖励左移。

本轮实现：

1. `traj_io.load`：未知首整数不再无条件当 v1 —— 必须满足历史契约
   （`sd ∈ {16,18,32,40}`、`na ∈ {27,64}`、`n ≤ MAX_STEPS`）才按 v1 解析，否则明确拒绝；
2. `traj_io.REJECT_STATS` + `reject_summary()`：所有拒绝路径**留痕**
   （原来全部静默 `return None`，调用方只计 `skipped` —— 格式事故表现为"样本量悄悄变少"）；
   `train_ppo.collect_data` 在 `skipped > 0` 时打印拒绝原因分布；
3. `train_ppo.load_model_bin`：补齐与 Java 对齐的校验（层数 1..8、尺寸 1..4096、
   `numLayers`/文件长度 vs 期望长度），尾部多余字节**打印提示**而不是静默忽略；
4. `selftest_contract.py[4]`：`SEMANTICS_EPOCH` 为正整数、Java `FORMAT_VERSION == traj_io.CURRENT_VERSION`、
   门禁键在落盘字典里、拒绝统计可得。

## 4. 附带发现并修复：快照水位线的"永久漏采"（新增 `train/seed_snapshot.py`）

`iterate.snapshot()` 用 `train/models/snapshot_state.txt` 记录"已快照到的最大 mtime"，
只拷贝 `mtime > 水位线` 的文件。**隐含前提**是水位线之前的文件都已在某个 session 里。
而"首轮部署前的初始快照由部署流程写入同一状态文件"（`iterate.py` docstring）——
部署时把水位线**直接写成 now**，两者之间就出现永久漏洞：那些文件的 mtime ≤ 水位线，
**此后任何一轮都不会再拷贝它们，且没有任何报错**。

责任方是**我自己**：`docs/P1修复记录_20260910.md:272` 记录了 P1 部署时
"把快照基线改为最后一次部署时刻（17:47）"——本意是不吃旧语义数据，副作用是把
"上一轮快照到重置瞬间"之间采集的数据一并永久丢弃。

实测：1,343 条轨迹从未进入任何 session（09-09: 451、09-10: 704、09-11: 186）。
其中今天的 186 条正是 16:20 轮快照之后到 16:33 重启之间采集的（约 13 分钟）。
这些文件是**惰性**的（mtime ≤ 水位线 → 永远不会被拷贝，因此也不会污染训练集）。

处置：

1. 新增 `train/seed_snapshot.py`：
   - `--verify`：自检"水位线之前是否还有没进过任何 session 的文件"（只读，发现即退出码 1）；
   - `--session-dir <dir>`：把活跃目录全部文件**逐条核验后**补拷进该 session，**全有或全无**，
     核验不过**不推进水位线**（避免制造新的漏采）——部署流程应改用这个，而不是直接写时间戳；
   - `--quarantine`：把孤儿移入 `trajectories_quarantine/`（保留数据、清空活跃目录）。
2. 已执行 `--quarantine`：1,343 条移入 `.../trajectories_quarantine`（85 MB，未删除）；
   复核不变式 → **OK: 水位线之前没有漏采文件**。

## 8. 事故：19:04 轮训练失败 —— 根因是本轮 P2-4 改动（已修复 + 补回归测试）

19:04 轮报"迭代失败/未产生新模型"。定位过程与结论：

### 8.1 直接原因

`train_ppo.py` 在收集僵尸轨迹时抛错：

```
691 files, skipped 691, stats={... 'kept': 0 ...}
[reject] unknown-version(first=600,sd=16,na=11)=687, unknown-version(first=4,sd=16,na=11)=2,
         unknown-version(first=177,sd=16,na=11)=1, header-over-limit=1
FileNotFoundError: no usable trajectories in ...\trajectories_zombie
iterate: training failed → skipping this round
```

即**我本轮加的"未知版本硬拒绝"白名单写错了**：`LEGACY_ACTION_DIMS` 我按代码注释推断为 `(27, 64)`，
而真实历史数据的动作维是 **11**（最早期只有通用动作、没有技能槽）。690 条 11 维历史轨迹被全数拒绝 →
僵尸轨迹集为空 → `collect_data` 抛 `FileNotFoundError` → 整轮失败。

**方法教训**：契约白名单不能按代码注释推断，必须扫真实产物。已改成扫全部轨迹目录文件头统计得出
（`sd ∈ {16,18,32,40}`、`na ∈ {11,27,64}`，注释里写明数据来源与这次教训）。

### 8.2 修复中的第二个坑（自己踩的）

第一版修复只加了 `na=11`，但仍拒绝 —— 因为回退分支**根本没读 `sd/na`**（`sd=0, na=0`），
而且回退时必须把文件指针**退回 12 字节**，否则会吃掉状态数组开头 4 字节（静默数据错位）。
现在头部解析统一为：先按 `[version, numSteps, sd, na]` 解释，若维度不合契约再按
`[numSteps, sd, na]` 解释（`f.seek(12)` 回退），两者都不合才拒绝。
这也顺带解决了**老格式 `numSteps` 恰好为 1/2/3 与版本号二义**的历史问题。

### 8.3 为什么自检全绿却炸了生产 —— 补上缺失的回归测试

`selftest_p0.py` 原本只覆盖 v1/v2/v3 的**正式写法**（`[version, numSteps, sd, na]`），
**从未覆盖三整数开头的老写法**（`[numSteps, sd, na]`）—— 而那正是生产里 691 条数据的格式。
新增第 [5] 节（8 条断言）：老写法 600/16/11 解析 + 数值/指针未错位、二义样本（numSteps=1）
判为老格式、未知版本头（4/600/40）必须拒绝、拒绝原因可观测。
