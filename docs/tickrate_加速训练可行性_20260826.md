# 技术分析：TickrateChanger（运算变速）加速训练可行性

> 源码：`E:\program\JAVA\TickrateChangerReborn`（TickrateChanger:Reborn，1.18.2，作者 MegaDarkness）
> 服务器内核验证：`server-1.20.1-20230612.114412-srg.jar` 反编译（`tools/tickrate_check/`）
> 分析日期：2026-08-26

## 1. 模组实现原理（源码事实，3 个文件即全部）

| 文件 | 机制 |
|---|---|
| `Main.java` | `PERCENT`（默认 20=正常）；`ScheduledExecutorService` 每 **1ms** 累加 `millisF += PERCENT/20.0`（虚拟毫秒）；`changeAll(percent)` 改倍率；`jump(ticks)` 给虚拟时钟 +ticks×50ms |
| `mixin/UtilMixin.java` | **`@Overwrite Util.getMillis()` → 返回虚拟时钟 `Main.millis`**（优先级 `Integer.MAX_VALUE`） |
| `TickrateCommand.java` | `/tickrate change <百分比>`、`/tickrate jump <刻>`（权限 2） |

**一句话原理**：虚拟化全局时钟源 `Util.getMillis()`——原版所有"等待/调度"都以它为基准，时钟加速 → 等待被跳过 → tick 连续执行。

## 2. 1.20.1 服务器 tick 循环是否依赖 `Util.getMillis()`？——**是（反编译实证）**

`MinecraftServer.runServer`（SRG `m_130011_`）核心循环：

```java
this.f_129726_ = Util.m_137550_();          // nextTickTime = Util.getMillis()
while (this.f_129764_) {
    long $$0 = Util.m_137550_() - this.f_129726_;   // getMillis() - nextTickTime
    if ($$0 > 2000L && ...) { /* "Can't keep up!" 追赶 */ }
    this.f_129726_ += 50L;                          // nextTickTime += 50ms
    ... tick 主体（世界/实体/任务）...
    this.f_129727_ = Math.max(Util.m_137550_() + 50L, this.f_129726_);
    this.m_130012_();   // manageBlock：阻塞直到 Util.getMillis() >= nextTickTime
}
// m_129960_：return this.m_18767_() || Util.m_137550_() < (...);
```

**tick 节流 = `Util.getMillis() < nextTickTime`**。虚拟时钟每秒多走（倍率×）→ 条件立即满足 → 50ms 等待被压缩 → **每秒真实执行 倍率×20 个游戏刻**。`PERCENT=200` = 40 TPS（2 倍速），`PERCENT=50` = 10 TPS（0.5 倍速）。✓ 与原版 TickrateChanger 的加速原理一致。

## 3. 对本模组训练环境的可行性——**成立，收益明确**

| 维度 | 分析 |
|---|---|
| **收益** | 我们的决策链全部按 **tickCount** 计（RL 5 tick / 战略层 40 tick / 冷却 / 缓冲）——tick 加速只缩短墙上时间，逻辑与数据语义**完全不变**；轨迹采集速率 ×倍率（如 1.5 倍速 → 每轮迭代数据量 +50%，迭代锚定仍是墙上 6h 不变） |
| **时序正确性** | `RlDataRecorder`/`RlTrace` 的时间戳用 `System.currentTimeMillis()`（真实时钟，不受 `Util.getMillis()` 虚拟化影响——mixin 只改 Util 返回值，不碰系统时钟）→ 轨迹文件名/CSV 时间戳真实 ✓ |
| **RCON / 训练流水线** | RCON 是独立线程（不受 tick 影响）；iterate.py 锚定用墙上 `time.time()` → 无需改动 ✓ |
| **声音副作用** | 客户端特性（服务器端无声卡/渲染），无影响 ✓ |
| **"Can't keep up" 日志** | 加速切换瞬间可能触发追赶警告（无害噪音） |
| **CPU 负载（主要风险）** | 每秒 tick 数 ×倍率 = 实体/动画/竞技场计算量 ×倍率。本机曾核显驱动崩溃（核显≠CPU，但负载敏感）→ **建议从 1.2~1.5 倍起步实测**，观察 CPU/温度与 TPS 实际达成率 |
| **`jump` 命令** | 瞬跳虚拟时钟会跳过调度等待（跳刻），对训练无价值且可能制造异常日志 → **不使用** |

## 4. 实施建议（合规：该模组 license = "All rights reserved"，**不搬运代码，独立重实现**）

思路（虚拟化时钟源驱动 tick 节流）是通用系统技术，本模组内部独立实现：

1. **`TickAccelerator`**（新类，`org.eftlm.stylish.util`）：`AtomicLong` 虚拟毫秒 + `ScheduledExecutorService`（每 1ms 累加 `1000×倍率/20`，与原作者 Timer 嵌套结构不同、字段/命名不同、无 Timer+TimerTask 组合）；`setMultiplier(float)` 运行时热调
2. **`UtilMixin` 等价 mixin**（本模组 `mixin/` 包）：`@Mixin(Util.class)` + `@Inject(method = "m_137550_", at = HEAD, cancellable = true)`（SRG 名，沿用 NullEntityMixin 的映射经验；用 @Inject 而非 @Overwrite，冲突容忍度更高）返回虚拟时钟；`@Pseudo` 不需要（Util 是原版类）；服务端专用
3. **配置与命令**：`rl.properties` 加 `tick_multiplier = 1.0`（1.0=20TPS 原速）；`/rl tickrate <倍率>` 热调（与 TickrateChanger 的 `/tickrate` 命令无冲突）；trace 事件 `tickrate_change`
4. **验证**：部署后 `/rl tickrate 1.5` → 观察 `/rl` heartbeat（每 100 tick 打点）墙上间隔应从 ~5s 缩至 ~3.3s → 确认加速生效；对比 1 小时轨迹条数与 CPU 占用；训练流水线零改动

## 6. 实施记录（2026-08-26 晚）：部署卡死根因与修复（重要）

### 6.1 症状

部署 tickrate 版 jar（292926B）后，服务器在 `Preparing start region` 卡死：
Server thread 在 `m_129940_`（prepareLevels）while 循环中 **RUNNABLE 忙等**（CPU 99% 单核），
全部 Worker-Main（chunk 生成）线程 WAITING（空闲）——**spawn chunks 生成任务从未被执行**。

### 6.2 根因：`Util.getMillis()` 已被第三方模组虚拟化（EFN UtilMixin）

日志实证（mixin handler 调试打印）：

```
[Tickrate] dbg active=true multiplier=1.0 virtualNow=1787753875139 realNow=72382 diff=1787753802757
```

- **`realNow`（`Util.getMillis()`）= 72382**——本服务器环境的 `Util.getMillis()` **已被
  EFN 模组的 UtilMixin 虚拟化为「游戏运行毫秒」（小数值）**（启动日志：
  `[EFN Mixin Loader] Apply Default Mixin: com.hm.efn.mixin.UtilMixin -> net.minecraft.Util.class`）。
- 原实现 `virtualNow() = baseMillis + (System.currentTimeMillis() - baseMillis) × multiplier`
  基于 **epoch 大数**（1.78e12）→ `virtualNow < nextTickTime` **恒 false** →
  `shouldKeepTicking()` 恒 false → `m_6362_`（任务可否执行，`task.tick+3 < tickCount || shouldKeepTicking()`）
  恒 false → **chunk 生成任务永不执行 → prepareLevels 死循环**。

### 6.3 修复（`TickAccelerator` + `TickrateMixin` 重写）

1. **虚拟时钟改为基于 `Util.getMillis()`（游戏时钟）缩放**：
   `virtualNow() = Math.round(Util.getMillis() × multiplier)`——与 tick 节流的 nextTickTime
   **同量级同源**；`multiplier=1.0` 时严格等于原版时钟（零副作用，已实证启动正常）。
2. **同源虚拟化 nextTickTime 写入点**：`@Redirect` 覆盖 `m_129960_`（shouldKeepTicking）、
   `m_130011_`（runServer 主循环 f_129727_）、`m_129940_`（prepareLevels f_129726_）内的
   `Util.m_137550_()`——比较两侧同为虚拟时钟，倍率 >1 时 50ms 虚拟间隔 = 50/倍率 真实毫秒（数学自洽）。
3. 移除 1ms 节拍累加器线程（不再需要，纯函数缩放即可）；保留 `/rl tickrate` 热调。
4. 调试日志（`n % 20000` 限频）仅用于定位，已从最终 jar 移除。

### 6.4 验证结果（2026-08-26 22:23 部署，multiplier=1.0）

- 启动 `Done (2.713s)`，RCON 就绪，竞技场/RL 心跳正常（100 tick / 5s）。
- `/rl tickrate 1.5` → 心跳间隔缩至 ~3.3s/100tick（**30 TPS 生效**）✓
- `/rl tickrate 1.0` → 恢复 5s/100tick ✓（倍率下调瞬间有一次追赶期，属正常）
- 训练流水线 iterate.py 全程未受影响（锚定墙上时钟，无需重启）。

### 6.5 遗留说明

- **MixinConnector 发现机制**：Mixin 0.8.5 的 ModLauncher 平台从 **jar MANIFEST 的
  `MixinConnector` 属性**发现 connector（参考 VIX 的 MANIFEST），`META-INF/mixin-connector.json`
  不被读取；本模组 jar 未写该属性 → `EftlmMixinConnector` 实际从未加载。但 mixins.json
  经 MANIFEST `MixinConfigs` 属性（MixinGradle 自动生成）正常注册生效，connector 是冗余件，
  保留不影响功能（后续可清理）。
- 若环境更换（无 EFN 或其他虚拟化 Util.getMillis 的 mod），本实现仍以 `Util.getMillis()`
  为基准 → 兼容原版时钟环境 ✓。

## 5. 结论

**可行**。1.20.1 服务器 tick 节流完全由 `Util.getMillis()` 驱动（反编译实证），虚拟化该时钟即可真实加速游戏刻；本模组的 RL/规则/数据链路全部 tick 计数且时间戳走系统时钟，加速对训练数据零污染，轨迹采集速率线性提升。主要代价是 CPU 负载随倍率上升，建议 1.2~1.5 倍起步。原模组为 All rights reserved，将按"独立重实现 + 致谢思路来源"处理（如需使用其 jar 或代码，另行联系作者 MegaDarkness 授权）。
